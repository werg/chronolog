# Performance: sync v3, kernel cost model and benchmarks

## Measure

```sh
pnpm bench                                   # kv + sql reducers, N = 100,500,1000
pnpm bench --sizes 400,2000 --reducers sql --json bench/results/run.json
BENCH_DEBUG=1 pnpm bench --sizes 50          # phase logging
pnpm tsx bench/vm.bench.ts                   # cost breakdown of one QuickJS reducer call
pnpm tsx bench/content.bench.ts              # blob/content pull: 1 and 16 MiB, 0 and 50 ms RTT
pnpm tsx bench/coldopen.bench.ts --sizes 400,2000,5000 --json bench/results/coldopen-after.json
pnpm tsx bench/coldopen.bench.ts --sizes 2000 --stores memory --scenarios reopen --reps 1 --profile /tmp/prof
```

`bench/coldopen.bench.ts` measures, per N (SQL reducer, private log): reopen of device + session
from a `MemoryBytesStore` and a `NativeBytesStore` (median of 3), the same with the persisted
materialized cache deleted, and a fresh peer's time to the author's revision ("first state") and
to completed synchronization, with snapshot bootstrap disabled (`snapshotBootstrap: false`, full
replay) and enabled. `--profile <dir>` writes a `.cpuprofile` per measured phase.

`bench/sync.bench.ts` reports, per log size N: local submit ms/op (first and last decile, so per-op
growth with N is visible), reopen, cold sync to a fresh peer (wall time and wire bytes each way),
steady-state live latency A→B, and reconnect with nothing new. Each phase also records
`perfCounters()` from `@chronolog/canonical`: SHA-256 calls and bytes, CBOR encode/decode,
Ed25519 sign/verify, QuickJS contexts and calls by method, kernel/session timings and wire
messages by kind. Counters are deterministic, so compare them when wall time is noisy.

## Sync v3 wire protocol

1. **Hello** carries only identity, nonce and the HPKE key share (no facts, no CAS). Proof completes
   the secure channel as before.
2. **Reconciliation rounds** (`recon`) compare fact-id sets per scope (`public` = public ops +
   finality checkpoints, `private` = encrypted envelopes) with range fingerprints over hex-prefix
   ranges (XOR of the first 16 id bytes plus count, `reconcile.ts`). Equal sets settle in one
   message each way; small ranges are exchanged as id lists, large differing ranges split 16-way.
   The owner ends a round with `recon-end`; the peer acks after merging everything sent before it.
3. Missing facts move as raw signed bytes in binary `facts` batches (≤ 512 KiB, canonical time
   order so receivers append at the tip). `want` requests specific ids.
4. **Live push**: every link pushes newly stored facts as they arrive, except to the link that
   delivered them.
5. **CAS is pulled, never pushed**: derived nodes (SQLite pages, reducer writes, seen-set nodes) are
   regenerated by deterministic replay; modules and other referenced nodes are requested with
   `cas-want` only when replay reports them missing. Standard modules are seeded by every replica.
6. **Retention receipts** are one signed statement per debounced batch (`items` = proposal ids),
   sent point-to-point to the peer that delivered the facts.
7. Membership is verified after the first public round (so in-flight admissions apply); private
   facts and content flow only after that.
8. **Snapshot bootstrap**: a replica with no history (`wantsSnapshotBootstrap()`: no private
   envelopes on a private log, no public ops on a public log, no frontier, no pending own ops)
   sends `snapshot-want`; the peer answers `snapshot` with its v3 bundle or null. Private logs ask
   right after membership is verified (posted before the public-round ack), public logs before
   the public round; the server posts the reply before handling anything after the request, so
   the snapshot is imported before the history facts arrive. Those facts still reconcile and are
   verified as usual, but ops covered by the snapshot frontier are not replayed.

Messages use a compact binary CBOR codec (`wire-codec.ts`) with a 13-byte fragment header; there is
no JSON or hex on the hot path.

## Kernel cost model

Per operation the kernel does O(changed state) work: copy-on-write topic record, per-topic content
hashes (`stateRoot` over topic hashes), append-only idempotency/outcome logs truncated on rewind,
lazy `ctx.topic()` / `ctx.opOutcome()` host calls instead of serializing all state into the VM,
positional snapshots (shallow copies), and query/describe caches keyed by the exact state they
observe. Session rematerialize reuses stable kernel inputs and diffs only the replayed suffix.

## Kernel lifetime

`TopicKernel.dispose()` releases the kernel's QuickJS runtimes, snapshots, logs and caches; it is
idempotent, keeps the committed revision and topics readable, and makes later
`materialize`/`query`/`describe` calls throw `SANDBOX_DISPOSED`. Hosts that build a kernel per
request (blind control replay) should dispose it when done. Sandboxes given a precompiled
`wasmModule` share one QuickJS WASM instance per module instead of instantiating one (16 MiB initial
heap) per kernel; isolation is unchanged because every call still runs in a fresh context.
`ApplicationSession` disposes swapped-out, ephemeral and closed kernels itself.

## Baseline vs sync v3 (2026-11-28, loaded 16-core machine, wall times noisy)

| N=400 | KV baseline | KV v3 | SQL baseline | SQL v3 |
|---|---|---|---|---|
| submit ms/op | 22 | 3.5–6 | 26 | 4.6–5.4 |
| cold sync | 4.8 s, 18.7 MB | 0.6 s, 154 KB | 9.0 s, 27.5 MB | 1.1 s, 154 KB |
| live op A→B | 90 ms, 90 KB | 7–25 ms, 0.5 KB | 254 ms, 113 KB | 17 ms, 0.5 KB |
| reconnect, nothing new | 7.8 s, 41.6 MB | 12–48 ms, 4.9 KB | 18.6 s, 60 MB | 29 ms, 4.9 KB |

Submit cost no longer grows with N (N=2000: ~6 ms/op flat). The largest remaining per-op cost is
the fresh QuickJS context and module evaluation per reducer call (~1 ms).

## Content transfer (lazy blob pipe)

- **Raw bytes end to end.** An encrypted chunk is stored and sent as
  `[format u8][epoch u64][nonce 12][AES-GCM ciphertext+tag]` (plaintext + 37 bytes); the binary
  wire codec carries it as a CBOR byte string. Public blob leaves are sent as their CAS bytes.
- **Streamed range requests.** `chunks-request` / `blob-chunks-request` name `start` + `count`
  (≤ 16) and are answered by one `chunk-response` / `blob-chunk-response` per chunk, in order, each
  sent only after the previous one was handed to the transport (per-request backpressure).
  `blob-info-response` also carries the blob DAG's interior nodes, so every leaf is verified by its
  own hash as it arrives. Up to 16 requests per peer each way; a busy peer answers `CONTENT_BUSY`.
  Content has its own ordered lane into the peer wire, so pipelining never overflows its queue.
- **Windowed multi-peer pull** (`content-pull.ts`): up to 4 MiB in flight ahead of the consumer,
  8-chunk batches spread over all attached sources; a chunk a source lacks or mis-delivers is
  retried on the next one. Streaming reads slow-start (window 1, doubling per chunk taken) so a
  reader that stops early fetches about what it read; retention and public blobs open the full
  window. Cancellation aborts every in-flight request (`cancel` frames).
- **Verify once.** A received chunk is hashed exactly once, inside `cas.putVerified` (stored with
  `cache: false`, so bulk content does not evict reducer pages from the CAS LRU). Locally stored
  chunks are not rehashed when served or read; local blob reads no longer rehash the whole blob,
  and serving a blob leaf no longer reassembles the whole blob per chunk.

`bench/content.bench.ts`, in-memory framed pair, pull on a synchronized fresh peer (loaded machine;
SHA-256 counters cover both peers in one process):

| blob | before | after | A→B wire bytes before → after |
|---|---|---|---|
| public 1 MiB, 0 / 50 ms RTT | 400 / 1190 ms | 75 / 170 ms | 1.34 MiB → 1.00 MiB |
| public 16 MiB, 0 / 50 ms RTT | 7.7 / 22.7 s | 0.70 / 0.82 s | 21.4 MiB → 16.06 MiB |
| private 1 MiB, 0 / 50 ms RTT | 1258 / 2125 ms | 50 / 293 ms | 2.67 MiB → 1.00 MiB |
| private 16 MiB, 0 / 50 ms RTT | 23.2 / 41.5 s | 0.85 / 1.76 s | 42.8 MiB → 16.07 MiB |

## Cold open and snapshot bootstrap

**Trust shortcuts** (accepted trade of transitory safety for speed; each is commented in code):

- *Own-store records on cold open.* Public ops are keyed by the op id verified at ingress, so
  reopen uses the key and a structural decode (`decodeTrusted*` in `@chronolog/protocol`: no
  canonical re-encode, no SHA-256). Encrypted envelopes are keyed by their digest. An envelope
  re-read from the store whose op id is in a persisted materialized cache, or is a pending op this
  device authored, is bound to that id by hashing its core bytes but not Ed25519-verified again;
  own pending ops reuse the plaintext kept in their `local-pending` record and are not decrypted.
  Envelopes received from peers are always decrypted and fully verified.
- *CAS preload* indexes nodes by key and decodes them on first read (hash = key).
- *IndexedDB record envelope v2* is `u8 2 | u16 keyLen | key | u32 CRC-32 | value`: key binding
  plus a corruption check, no SHA-256 or canonical CBOR per record.
- *Device open* batches its metadata reads into one `getMany` and runs the signer sign/verify
  self-test once per key per process instead of on every activation.
- *Snapshot adoption.* A fresh replica adopts a member-signed snapshot as its frontier without
  replaying the history it summarizes. The bundle signature (Ed25519, domain
  `chronolog/materialized-snapshot/v3`) is always checked, the signer must be a member under the
  permissions the replica knows, private-log bundles are AES-GCM encrypted under the epoch key, and
  CAS nodes are re-hashed. Facts received afterwards are verified individually.

**Materialized cache** (`materialized-cache` key, `encodeMaterializedCache` in
`@chronolog/materializer`): binary header JSON (topics, roots, digests, author table, last op per
topic) + raw 32-byte frontier and suffix op ids + positional outcome tuples. Restore maps suffix
ids to inputs in O(N) without re-sorting and never re-reads op updates. It is written right after
the first materialization of a replica, debounced (1.5 s) afterwards, on close, on page hide
(`visibilitychange`/`pagehide` where a document exists) and via `flushMaterializedCache()`; an
unchanged cache is not rewritten after open.

**Snapshot bundle v3** (`snapshot-codec.ts`): `[3, logId, 0, signer, sig, body]` or
`[3, logId, 1, epoch, nonce, AES-GCM([signer, sig, body])]`, body = `[logId, frontier-only cache,
reachable CAS nodes]`. It carries no outcomes or events: size is the reachable state (SQLite pages,
seen set) plus 32 bytes per covered op. The same bytes serve the wire `snapshot` message and the
host path (`exportMaterializedSnapshot()` / `importMaterializedSnapshot()` /
`materializedSnapshot` open option). A snapshot-bootstrapped replica reports outcomes and events
only for ops after its frontier.

**Frontier rewinds.** An op that sorts at or before the frontier's latest timestamp (or a rewind
below a restored suffix) makes the kernel throw `KERNEL_FRONTIER_REWIND`; the session then drops
the frontier and replays every op it holds, so ordering stays deterministic.

## QuickJS reducer invocation fixed cost

Every `reduce`/`query`/`describe`/`onConflict`/`derive` call still runs in a fresh
`QuickJSContext` (pristine globals and module instances, see the CRDT contract). What changed is the
work done around that context:

- **No per-call JS stub.** The `ctx` argument and the run step used to be an entry-module string
  (~10 closures) compiled in every context; compiling it was the largest cost after context creation.
  `ctx` is now built from host functions plus two one-line helpers returned by the prelude eval
  (`makeCtx` freezes the members, `finish` is `JSON.stringify({ __ok: true, value })`). The entry
  module only re-exports the target export, and the reducer is called with `callFunction`, so the
  separate run eval and the env global are gone. Semantics are kept member for member (order,
  freezing, `String()` coercion, topic-object identity, `toJSON(key)`, argument positions, error
  codes); `ctx.mount()` keeps its JS body, compiled only on first use. The `ctx` tests in
  `quickjs-sandbox.test.ts` pass against both the old and the new implementation.
- **No Date intrinsic.** Contexts are created without it (~10% of context creation). The prelude
  still defines `Date` as a non-writable `undefined`. In quickjs-ng that intrinsic also installs
  `performance`, whose `now()` returned wall-clock time inside reducers and was never stripped; it is
  gone now.
- **Builtin bridges on demand.** `globalThis.__chronologHost` methods for `chronolog:crypto`,
  `chronolog:cas`, `chronolog:wasm` and `chronolog:sqlite` are created only when that builtin's shim
  module is loaded (module loading finishes before any module body runs). They used to be created
  for every call, whether the builtin was enabled or not. `readTopic`/`opOutcome`/`queryTopic`/
  `queryMount` are no longer exposed on it, because `ctx` calls the host directly.

Measured in one process, old and new interleaved, minimum over 20 rounds (machine load average
16–26, so the absolute figures are inflated; the ratios are what to compare):

| per call | before | after | change |
|---|---|---|---|
| trivial KV reduce | 0.93–1.14 ms | 0.70–0.79 ms | −25 to −31% |
| SQL reduce (`chronolog:sqlite`, fresh db) | 2.2–5.2 ms | 1.9–3.5 ms | −4 to −32% (SQLite-dominated) |
| `chronolog/permissions` query (600-line std module) | 5.0–5.6 ms | 4.8–5.5 ms | −3% (compile-dominated) |

`pnpm tsx bench/vm.bench.ts` (min-of-rounds) breaks it down. At load ~8: context creation 0.30 ms
(0.25 ms without Date), determinism prelude +0.05–0.07 ms, kv module import +0.04 ms. The
permissions module import is +2.9 ms, nearly all of it compiling the source. The end-to-end
`pnpm bench --sizes 400,2000 --reducers kv,sql` runs (before/after JSON in
`bench/results/vm-{before,after}-kv-sql.json`, A/B in `bench/results/vm-invoke-ab.json`) could not resolve a ~0.3 ms/op gain under that load: submit ms/op varied
by 2× between identical runs. Their deterministic counters (`vm.*`, `vm.newContext`) are identical
before and after.

Ideas evaluated and not done:

- **Reusing a context, or batching one op's updates into one context.** Module instances and
  globals are per context, so state left by one call (module `let`s, `globalThis`, prototype
  pollution, mutated `ctx.topic()` objects) would be visible to the next. That breaks the
  fresh-context invariant and the leakage tests, so it is not done.
- **Folding the old stub into one global script with bound dispatchers.** Measured slower: the cost
  is compiling the closures, not the number of evals.
- **Bypassing the entry module** by evaluating the target module under its canonical name. That
  would save one tiny module, but module-load error details (which can end up in rejected outcomes)
  would differ from older replicas.
- **Bytecode caching (the real win for std modules).** A module compiled in one context cannot be
  run in another: bytecode keeps its realm and would resolve globals in the old context. Caching
  therefore means serializing bytecode once per module hash and reading it into each fresh context.
  The stock `@jitl/quickjs-ng-wasmfile-release-sync` build cannot do this. `QTS_bjson_encode` and
  `QTS_bjson_decode` call `JS_WriteObject`/`JS_ReadObject` with flags `0`, and reading bytecode fails
  with "no bytecode allowed". The FFI also has no call to run a read module. A custom wasm build would
  need:
  1. `QTS_bjson_encode(ctx, val, JS_WRITE_OBJ_BYTECODE)` on a `compileOnly` module.
  2. `QTS_bjson_decode(ctx, data, JS_READ_OBJ_BYTECODE)`.
  3. A new `QTS_EvalModuleBytecode(ctx, val)` doing `JS_ResolveModule` + `JS_EvalFunction` and
     registering the module under its canonical name.

  Bytecode would be cached per CAS hash in `#moduleCache`, and the bytecode format would be pinned
  with `QUICKJS_RUNTIME_ID`. Expected gain: most of the 2.9 ms compile of `chronolog/permissions` (and
  ~0.04 ms for small reducers), leaving deserialization, estimated at 0.2–0.4 ms for that module.
