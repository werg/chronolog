# Performance: sync v3, kernel cost model and benchmarks

## Measure

```sh
pnpm bench                                   # kv + sql reducers, N = 100,500,1000
pnpm bench --sizes 400,2000 --reducers sql --json bench/results/run.json
BENCH_DEBUG=1 pnpm bench --sizes 50          # phase logging
pnpm tsx bench/vm.bench.ts                   # cost breakdown of one QuickJS reducer call
pnpm tsx bench/content.bench.ts              # blob/content pull: 1 and 16 MiB, 0 and 50 ms RTT
```

`bench/sync.bench.ts` reports, per log size N: local submit ms/op (first and last decile, so per-op
growth with N is visible), reopen, cold sync to a fresh peer (wall time and wire bytes each way),
steady-state live latency A→B, and reconnect with nothing new. Each phase also records
`perfCounters()` from `@chronolog/canonical`: SHA-256 calls and bytes, CBOR encode/decode,
Ed25519 sign/verify, QuickJS contexts and calls by method, kernel/session timings and wire
messages by kind. Counters are deterministic, so compare them when wall time is noisy.

## Sync v3 wire protocol

1. **Hello** carries only identity, nonce and the HPKE key share (no facts, no CAS). Proof completes
   the secure channel as before.
2. **Reconciliation rounds** (`recon`) compare fact-id sets per scope (`public` = public ops +
   finality checkpoints, `private` = encrypted envelopes) with range fingerprints over hex-prefix
   ranges (XOR of the first 16 id bytes plus count, `reconcile.ts`). Equal sets settle in one
   message each way; small ranges are exchanged as id lists, large differing ranges split 16-way.
   The owner ends a round with `recon-end`; the peer acks after merging everything sent before it.
3. Missing facts move as raw signed bytes in binary `facts` batches (≤ 512 KiB, canonical time
   order so receivers append at the tip). `want` requests specific ids.
4. **Live push**: every link pushes newly stored facts as they arrive, except to the link that
   delivered them.
5. **CAS is pulled, never pushed**: derived nodes (SQLite pages, reducer writes, seen-set nodes) are
   regenerated by deterministic replay; modules and other referenced nodes are requested with
   `cas-want` only when replay reports them missing. Standard modules are seeded by every replica.
6. **Retention receipts** are one signed statement per debounced batch (`items` = proposal ids),
   sent point-to-point to the peer that delivered the facts.
7. Membership is verified after the first public round (so in-flight admissions apply); private
   facts and content flow only after that.

Messages use a compact binary CBOR codec (`wire-codec.ts`) with a 13-byte fragment header; there is
no JSON or hex on the hot path.

## Kernel cost model

Per operation the kernel does O(changed state) work: copy-on-write topic record, per-topic content
hashes (`stateRoot` over topic hashes), append-only idempotency/outcome logs truncated on rewind,
lazy `ctx.topic()` / `ctx.opOutcome()` host calls instead of serializing all state into the VM,
positional snapshots (shallow copies), and query/describe caches keyed by the exact state they
observe. Session rematerialize reuses stable kernel inputs and diffs only the replayed suffix.

## Kernel lifetime

`TopicKernel.dispose()` releases the kernel's QuickJS runtimes, snapshots, logs and caches; it is
idempotent, keeps the committed revision and topics readable, and makes later
`materialize`/`query`/`describe` calls throw `SANDBOX_DISPOSED`. Hosts that build a kernel per
request (blind control replay) should dispose it when done. Sandboxes given a precompiled
`wasmModule` share one QuickJS WASM instance per module instead of instantiating one (16 MiB initial
heap) per kernel; isolation is unchanged because every call still runs in a fresh context.
`ApplicationSession` disposes swapped-out, ephemeral and closed kernels itself.

## Baseline vs sync v3 (2026-11-28, loaded 16-core machine, wall times noisy)

| N=400 | KV baseline | KV v3 | SQL baseline | SQL v3 |
|---|---|---|---|---|
| submit ms/op | 22 | 3.5–6 | 26 | 4.6–5.4 |
| cold sync | 4.8 s, 18.7 MB | 0.6 s, 154 KB | 9.0 s, 27.5 MB | 1.1 s, 154 KB |
| live op A→B | 90 ms, 90 KB | 7–25 ms, 0.5 KB | 254 ms, 113 KB | 17 ms, 0.5 KB |
| reconnect, nothing new | 7.8 s, 41.6 MB | 12–48 ms, 4.9 KB | 18.6 s, 60 MB | 29 ms, 4.9 KB |

Submit cost no longer grows with N (N=2000: ~6 ms/op flat). The largest remaining per-op cost is
the fresh QuickJS context and module evaluation per reducer call (~1 ms).

## Content transfer (lazy blob pipe)

- **Raw bytes end to end.** An encrypted chunk is stored and sent as
  `[format u8][epoch u64][nonce 12][AES-GCM ciphertext+tag]` (plaintext + 37 bytes); the binary
  wire codec carries it as a CBOR byte string. Public blob leaves are sent as their CAS bytes.
- **Streamed range requests.** `chunks-request` / `blob-chunks-request` name `start` + `count`
  (≤ 16) and are answered by one `chunk-response` / `blob-chunk-response` per chunk, in order, each
  sent only after the previous one was handed to the transport (per-request backpressure).
  `blob-info-response` also carries the blob DAG's interior nodes, so every leaf is verified by its
  own hash as it arrives. Up to 16 requests per peer each way; a busy peer answers `CONTENT_BUSY`.
  Content has its own ordered lane into the peer wire, so pipelining never overflows its queue.
- **Windowed multi-peer pull** (`content-pull.ts`): up to 4 MiB in flight ahead of the consumer,
  8-chunk batches spread over all attached sources; a chunk a source lacks or mis-delivers is
  retried on the next one. Streaming reads slow-start (window 1, doubling per chunk taken) so a
  reader that stops early fetches about what it read; retention and public blobs open the full
  window. Cancellation aborts every in-flight request (`cancel` frames).
- **Verify once.** A received chunk is hashed exactly once, inside `cas.putVerified` (stored with
  `cache: false`, so bulk content does not evict reducer pages from the CAS LRU). Locally stored
  chunks are not rehashed when served or read; local blob reads no longer rehash the whole blob,
  and serving a blob leaf no longer reassembles the whole blob per chunk.

`bench/content.bench.ts`, in-memory framed pair, pull on a synchronized fresh peer (loaded machine;
SHA-256 counters cover both peers in one process):

| blob | before | after | A→B wire bytes before → after |
|---|---|---|---|
| public 1 MiB, 0 / 50 ms RTT | 400 / 1190 ms | 75 / 170 ms | 1.34 MiB → 1.00 MiB |
| public 16 MiB, 0 / 50 ms RTT | 7.7 / 22.7 s | 0.70 / 0.82 s | 21.4 MiB → 16.06 MiB |
| private 1 MiB, 0 / 50 ms RTT | 1258 / 2125 ms | 50 / 293 ms | 2.67 MiB → 1.00 MiB |
| private 16 MiB, 0 / 50 ms RTT | 23.2 / 41.5 s | 0.85 / 1.76 s | 42.8 MiB → 16.07 MiB |

SHA-256 for a private 16 MiB pull fell from 128 MiB hashed to 32 MiB (one hash on the sender's
store read, one on receipt); private 16 MiB `put` fell from ~3–4.8 s to ~0.5 s. Raw results:
`bench/results/content-before.json`, `bench/results/content-after.json`.
